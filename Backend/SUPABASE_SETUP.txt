SUPABASE SETUP ON THE LINUX LAPTOP
Road Quality Mapper - EE475 Team 5
==================================================================

These steps assume Ubuntu/Debian. Other distros work too; only the package commands change.
Supabase runs in Docker containers, managed by the Supabase CLI.

Anything in <angle brackets> is a placeholder you fill in.


------------------------------------------------------------------
STEP 1 - Prepare the laptop
------------------------------------------------------------------

    sudo apt update && sudo apt upgrade -y
    sudo apt install -y git curl ca-certificates postgresql-client

(postgresql-client gives you `psql`, which is handy for loading SQL files.)

The laptop is acting as a server, so stop it from sleeping when the lid closes:

    sudo nano /etc/systemd/logind.conf
        # set these lines (remove the leading #):
        HandleLidSwitch=ignore
        HandleLidSwitchExternalPower=ignore
    sudo systemctl restart systemd-logind

Also turn off automatic suspend in Settings > Power.


------------------------------------------------------------------
STEP 2 - Install Docker
------------------------------------------------------------------

    curl -fsSL https://get.docker.com | sudo sh
    sudo usermod -aG docker $USER

Log out and back in (or reboot) so the group change applies, then check it:

    docker run hello-world

You should see "Hello from Docker!". If you get "permission denied", you haven't
logged out and back in yet.

Make Docker start on boot:

    sudo systemctl enable docker


------------------------------------------------------------------
STEP 3 - Install the Supabase CLI
------------------------------------------------------------------

Download the latest Linux release and put it on your PATH:

    cd /tmp
    curl -LO https://github.com/supabase/cli/releases/latest/download/supabase_linux_amd64.tar.gz
    tar -xzf supabase_linux_amd64.tar.gz
    sudo mv supabase /usr/local/bin/
    supabase --version

(If the laptop is ARM, use supabase_linux_arm64.tar.gz instead. You can also install the
.deb from https://github.com/supabase/cli/releases if you prefer.)


------------------------------------------------------------------
STEP 4 - Set up Git and clone the repo
------------------------------------------------------------------

    git config --global user.name  "<Your Name>"
    git config --global user.email "<your-github-email>"

Sign in to GitHub. The easiest way is the GitHub CLI:

    sudo apt install -y gh
    gh auth login          # choose GitHub.com > HTTPS > log in with a web browser

Clone the repo and make a branch for this work:

    cd ~
    git clone https://github.com/henryqla/ee475aut26team5.git
    cd ee475aut26team5
    git checkout -b supabase-init


------------------------------------------------------------------
STEP 5 - Initialize Supabase inside Backend/
------------------------------------------------------------------

    cd ~/ee475aut26team5/Backend
    supabase init

When it asks about VS Code / IntelliJ Deno settings, answering "N" is fine.

This creates:

    Backend/supabase/
        config.toml      <- project settings (ports, auth, etc.). COMMIT THIS.
        .gitignore       <- already ignores the generated temp files and .env
        seed.sql         <- may or may not be created; not used (vehicles come from a migration)

The CLI expects migrations and functions INSIDE that supabase/ folder, so move the
placeholder folders we already have in there:

    git mv migrations supabase/migrations
    git mv functions  supabase/functions

(If git complains that a target already exists, move the .gitignore files over by hand
and delete the empty old folders.)

The final layout should be:

    Backend/
        sample_data.sql
        SUPABASE_SETUP.txt
        supabase/
            config.toml
            .gitignore
            migrations/
            functions/

Note: the add-supabase-folders branch on GitHub named this folder "SupaBase". We're using
Backend/supabase/ (lowercase, the CLI default) going forward, so don't follow that name.
The CLI only finds a folder named exactly "supabase" containing config.toml, and Linux
file names are case-sensitive, so "SupaBase" would not be found. Keeping it inside
Backend/ keeps all backend files in one place, next to android_app/ for the app.


------------------------------------------------------------------
STEP 6 - Start Supabase
------------------------------------------------------------------

    cd ~/ee475aut26team5/Backend
    supabase start

The first run downloads several Docker images and takes a few minutes. When it's done
it prints something like:

    API URL:         http://127.0.0.1:54321
    DB URL:          postgresql://postgres:postgres@127.0.0.1:54322/postgres
    Studio URL:      http://127.0.0.1:54323
    anon key / Publishable key:     eyJ...  (or sb_publishable_...)
    service_role key / Secret key:  eyJ...  (or sb_secret_...)

Save that output somewhere private (NOT in the repo). You can print it again any time:

    supabase status

Open Studio in the laptop's browser at http://127.0.0.1:54323 - this is the dashboard
for browsing tables, running SQL, and viewing logs.

KEY RULES:
  - The anon / publishable key is what the Android app uses. It's fine for it to be on
    the phone, but still keep it out of Git (put it in android_app/local.properties).
  - The service_role / secret key bypasses all security. Never put it in the app or Git.


------------------------------------------------------------------
STEP 7 - Load the database schema
------------------------------------------------------------------

The tables, checks and access rules are already written as migrations in
Backend/supabase/migrations/ (they follow docs/data-contract.md section 7):

    <timestamp>_init_schema.sql    PostGIS, the 4 tables, permissions, Row Level Security
    <timestamp>_add_vehicles.sql   the starting vehicle list (truck, camry, escape)

Get the latest files, restart Supabase so it picks up config.toml (anonymous sign-in is
turned on there), and build the database:

    cd ~/ee475aut26team5
    git pull
    cd Backend
    supabase stop && supabase start
    supabase db reset

`db reset` wipes the database and runs every migration in order. It's fine now because
there's no real data yet. There is no seed.sql; if the CLI prints a warning that it can't
find one, ignore it.

Ignore Backend/sample_data.sql. It was an early experiment and doesn't match the contract.
If you loaded it before, `db reset` removes its tables.


------------------------------------------------------------------
STEP 8 - Check it worked, and how to apply changes later
------------------------------------------------------------------

Check:
    - Studio > Table Editor shows vehicles, trips, segments, events.
    - vehicles has 3 rows.
    - The API answers with the anon key (use the key from `supabase status`):

        curl http://127.0.0.1:54321/rest/v1/vehicles \
             -H "apikey: <anon-key>" -H "Authorization: Bearer <anon-key>"

      This should print the 3 vehicles.
    - The anon key alone can't write (only the signed-in app can). This should fail with
      a permission / row-level security error:

        curl -X POST http://127.0.0.1:54321/rest/v1/vehicles \
             -H "apikey: <anon-key>" -H "Authorization: Bearer <anon-key>" \
             -H "Content-Type: application/json" \
             -d '{"id":"test","name":"Test","type":"sedan"}'

If `db reset` stops with an error, copy the whole output; the migration needs fixing,
not the database.

Changing the schema later:
    - Every change gets a NEW migration file. Never edit a migration that has already run
      on the laptop, and don't just click changes in Studio, or the rest of the team (and
      the next `db reset`) won't get them.

        supabase migration new <short_name>

    - Change docs/data-contract.md first, so the app team knows.

Applying new migrations once real drives are stored:

    supabase migration up

This runs only the migrations that haven't run yet and keeps the data.
DON'T use `supabase db reset` after that point: it deletes every trip.


------------------------------------------------------------------
STEP 9 - Let the phone reach the laptop
------------------------------------------------------------------

The phone is usually on cellular data while driving, so it can't see the laptop on the
home Wi-Fi. We use Tailscale Funnel: it gives the laptop a fixed public HTTPS URL
(https://<machine-name>.<tailnet-name>.ts.net) that forwards to port 54321 only. It's
free, needs no router changes, and the phones don't need any extra app.

What Funnel exposes: ONLY the Supabase API gateway on port 54321 (REST, auth, storage,
edge functions). Not SSH, not your files, not the database port, not Studio. But it IS
on the public internet, so do 9B before 9C.

--- 9A. Quick test on the same Wi-Fi (optional) ---

    hostname -I                       # first address, e.g. 192.168.1.42
    sudo ufw allow 54321/tcp          # only if ufw firewall is enabled

From another device on the same Wi-Fi, check that the API answers (use your anon key):

    curl http://<laptop-ip>:54321/rest/v1/vehicles \
         -H "apikey: <anon-key>" -H "Authorization: Bearer <anon-key>"

You should get JSON back. This is plain http://, which Android blocks by default, so the
app would need a network security config allowing cleartext to that IP. With Funnel
(9C) the app uses https:// and doesn't need that.

--- 9B. Lock it down BEFORE going public ---

1) Replace the default keys. Every Supabase CLI install ships with the SAME JWT secret,
   publishable key and secret key, built into the program and published online. Anyone
   could use them to read or delete everything. config.toml ([auth] section) already
   points at your own values; you create them on the laptop. Both files below are in
   Backend/.gitignore, so they can't be committed by accident.

   a) A signing key (signs the tokens the app gets when it signs in):

       cd ~/ee475aut26team5/Backend
       supabase gen signing-key --algorithm ES256 > supabase/signing_keys.json

      Open the file and make sure it starts with [ and ends with ]. If it starts with {,
      add [ at the very start and ] at the very end.

   b) Random values for the other keys, in Backend/.env (copy exactly):

       cat > .env <<EOF
       SUPABASE_AUTH_JWT_SECRET=$(openssl rand -hex 32)
       SUPABASE_AUTH_PUBLISHABLE_KEY=sb_publishable_$(openssl rand -hex 16)
       SUPABASE_AUTH_SECRET_KEY=sb_secret_$(openssl rand -hex 16)
       EOF
       chmod 600 .env supabase/signing_keys.json

   c) Restart and check:

       supabase stop && supabase start
       bash check_keys.sh

      Every line should say PASS. If not, send the output (it contains no keys).

   d) `supabase status` now shows the new publishable key. Give that to the app team
      (with the Funnel URL); the old one stops working.

   Don't run `git status` and commit if .env or signing_keys.json show up; they shouldn't.
   If you lose them, make new ones the same way; the app team then needs the new
   publishable key.

2) Row Level Security on every table. The publishable key ships inside the APK, so treat
   it as public. RLS policies are the only thing deciding what it can do. They're already
   in the init_schema migration (loaded in Step 7) and follow docs/data-contract.md
   section 7 "Who can do what". Check they work:

       cd ~/ee475aut26team5/Backend
       bash check_access.sh

   Every line should say PASS. It adds a test trip and two test users and deletes them
   again. Any change to the rules goes in a new migration, never just in Studio; run the
   script again afterwards.

--- 9C. Install Tailscale and turn on Funnel ---

Install and log in (the login URL it prints can be opened on any device):

    curl -fsSL https://tailscale.com/install.sh | sh
    sudo systemctl enable --now tailscaled
    sudo tailscale up

In the admin console (https://login.tailscale.com/admin):
    - Settings: turn on two-factor auth for the account you logged in with. Whoever has
      this account controls the laptop's network access.
    - DNS: turn on MagicDNS and HTTPS Certificates (Funnel needs both).
    - Machines > <laptop> > ... > Disable key expiry. Otherwise the laptop drops off
      after ~180 days and the URL stops working.

Turn on Funnel for the Supabase API:

    sudo tailscale funnel --bg 54321

The first time, it may print a link to enable Funnel for your tailnet. Open it, approve,
then run the command again. It prints the public URL, e.g.

    https://<machine-name>.<tailnet-name>.ts.net

--bg keeps Funnel running in the background and turns it back on after a reboot. Check
or turn it off with:

    tailscale funnel status
    sudo tailscale funnel reset       # turn Funnel off

Test from a phone with Wi-Fi OFF (on cellular), or any computer off your network:

    curl https://<machine-name>.<tailnet-name>.ts.net/rest/v1/vehicles \
         -H "apikey: <anon-key>" -H "Authorization: Bearer <anon-key>"

Give the app team the https://...ts.net URL and the new anon key. They go in
android_app/local.properties, never hard-coded, so the URL can change later (e.g. if we
move to a Cloudflare Tunnel with our own domain) without code changes.

Notes:
    - The ts.net hostname shows up in public certificate logs, so bots WILL find it and
      send junk requests. That's harmless if 9B is done. It's also why 9B matters.
    - Funnel has bandwidth limits. Small JSON uploads from a few phones are fine.
    - Your home IP is not exposed.
    - NEVER funnel 54322 (database) or 54323 (Studio).
    - If Supabase isn't running, Funnel returns an error page. Funnel comes back after a
      reboot, Supabase doesn't (see Everyday Commands).

STEP 10 - Commit the Supabase files to GitHub
------------------------------------------------------------------

First check what's about to be committed:

    cd ~/ee475aut26team5
    git status

You SHOULD see:
    Backend/supabase/config.toml
    Backend/supabase/.gitignore
    Backend/supabase/migrations/...

Commit and push:

    git add Backend
    git commit -m "Initialize Supabase project in Backend/"
    git push -u origin supabase-init

Open a pull request so the team can review it:

    gh pr create --base main --title "Initialize Supabase project" \
                 --body "Runs supabase init in Backend/ and moves migrations/functions into it."

(or open the repo on github.com and click "Compare & pull request").

After it's merged, teammates who want their own local copy can pull, install Docker +
the CLI (Steps 2-3), and run `supabase start` then `supabase db reset` in Backend/.


------------------------------------------------------------------
EVERYDAY COMMANDS (run inside Backend/)
------------------------------------------------------------------

    supabase start            start everything (data is kept between restarts)
    supabase stop             stop everything, keep data
    supabase status           show URLs and keys again
    supabase migration up     run new migrations, keep data (use this once real drives exist)
    supabase db reset         wipe DB, re-run all migrations (DELETES ALL DATA)
    supabase migration new X  create a new empty migration file
    supabase stop --no-backup stop AND delete all data (careful)

Supabase does not restart on its own after a reboot. After the laptop restarts, run
`supabase start` in Backend/ again.


------------------------------------------------------------------
TROUBLESHOOTING
------------------------------------------------------------------

"Cannot connect to the Docker daemon"
    sudo systemctl start docker   (and make sure you're in the docker group, Step 2)

"port is already allocated"
    Something else is using 5432x. `supabase stop`, or change the ports in config.toml.

Phone gets "connection refused" / timeout
    - Check the curl test from Step 9 works from another computer first.
    - Using the https://...ts.net URL, not a LAN IP, 127.0.0.1 or localhost?
    - On the laptop: `supabase status` (is it running?) and `tailscale funnel status`
      (is Funnel on?). `tailscale status` should show the laptop as online.

Funnel URL worked before, now it doesn't
    - Laptop asleep or rebooted? Supabase needs `supabase start` again after a reboot.
    - Laptop's Tailscale key expired? Log in again with `sudo tailscale up` and disable
      key expiry for it in the admin console (Step 9C).

Phone gets "CLEARTEXT communication not permitted"
    The app is using an http:// LAN address. Use the https://...ts.net URL instead
    (or, for LAN-only testing, add a network security config; see Step 9A).

Old default keys still work after changing them
    Supabase didn't pick up the new secret. Check config.toml, the env var it points to,
    then `supabase stop && supabase start`.

Queries from the app return [] but Studio shows rows
    Row Level Security is blocking the anon role. Check the policies on that table.
